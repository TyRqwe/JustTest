## 1. `01_setup.py` — установка и подготовка БД

### 1.1. `pg_hba.conf` менялся на `trust`

**Проблема.** Скрипт прописывал `trust` сразу для двух строк локальных подключений. На облачной ВМ с публичным IP даже на короткое окно это даёт любому процессу на машине логиниться суперпользователем без пароля.

**Решение.** Совсем не трогать `pg_hba.conf`. Все вызовы дальше идут как `sudo -u postgres psql ...`, а это unix-сокет с `peer` → проверка по UID процесса. На дефолтной Ubuntu/Debian это работает «из коробки».

**Почему не альтернатива `peer map`/`scram-sha-256`.** Любая правка `pg_hba.conf` — это новая точка поломки и зависимость от формата файла конкретного дистрибутива. `peer` через `sudo -u postgres` решает задачу без правки конфига.

### 1.2. `sed` поверх `pg_hba.conf` хрупкий

Снято вместе с пунктом 1.1: правок больше нет.

### 1.3. `/tmp/setup.sql` ломается на systemd `PrivateTmp=yes`

**Проблема.** Скрипт пишет SQL в `/tmp/setup.sql` от root, потом запускает `sudo -u postgres psql -f /tmp/setup.sql`. У юнита `postgresql.service` на современных Debian/Ubuntu включён `PrivateTmp=yes`, и `/tmp` — изолированный, файла, написанного снаружи, postgres не видит.

**Решение.** Передавать SQL в `psql` через stdin (`psql -v ON_ERROR_STOP=1`). Никаких временных файлов вообще.

### 1.4. `time.sleep(2)` после `systemctl restart`

**Проблема.** Не детерминированно. На медленной ВМ может быть мало, на быстрой — лишняя задержка.

**Решение.** `pg_isready -t 30`. Стандартный механизм для синхронного ожидания готовности postgres.

### 1.5. Дублирующий индекс `idx_test_data_id`

**Проблема.** `id SERIAL PRIMARY KEY` уже создаёт btree, после чего `CREATE INDEX idx_test_data_id ON test_data(id)` создаёт **второй** такой же.
Это мёртвый индекс, который вдобавок искажает write-нагрузку: при каждом UPDATE постgres платит за поддержание двух btree, плюс HOT-update не сработает.

**Решение.** Убрать `CREATE INDEX`.

### 1.6. Молчаливый отказ на non-Debian дистрибутивах

**Решение.** В начале проверять `/etc/os-release` на `ID_LIKE=debian` (или `ID` в `{ubuntu, debian}`); иначе выйти с понятным сообщением.

## 2. `02_bench.py` — бенч

### 2.1. Методологическая проблема №1: `auto_choose_target` + таймаут

**Проблема.** Одновременно два ограничителя — фиксированная цель в операциях и таймаут 120 с. На быстром железе цель в 1000 операций выполняется за 2 секунды (мало точек для статистики, шум доминирует); на медленном — упирается в таймаут и тест отчитывается как незавершённый.

**Решение.** Полностью убрать понятие «цели в операциях». Тест — это **фиксированное окно времени** (`TEST_DURATION = 120`), за которое мы считаем: сколько транзакций успели, какой средний TPS и распределение латентности.

**Почему так.** Это стандартный подход pgbench: ограничиваем время, измеряем throughput + latency. Сравнение конфигов ВМ тогда сводится к сопоставлению TPS и латентности при равном бюджете времени.

### 2.2. Методологическая проблема №2: autovacuum во время теста

**Проблема.** Случайный UPDATE плодит dead tuples; autovacuum просыпается прямо во время теста и шумит CPU/диск/латентность.

**Решение.** На время бенча отключать autovacuum для целевой таблицы:
```sql
ALTER TABLE test_data SET (autovacuum_enabled = false);
```
В `finally` обязательно возвращать `true`, чтобы не оставить таблицу с выключенным автоваккумом надолго.

### 2.3. Методологическая проблема №3: общее состояние таблицы

**Проблема.** Probe и реальный тест шли друг за другом по одной таблице без сброса состояния. Многопоточный SELECT после single-thread UPDATE — это уже почти прогретый кэш страниц.

**Решение.** `VACUUM (ANALYZE) test_data` между фазами. Это даёт предсказуемое состояние видимости/статистики.

**Что осталось «как есть».** Сбрасывать page cache (`drop_caches`) мы не делаем: это требует root внутри ВМ и портит сравнимость с прогонами без сброса. Документируем явно: тест измеряет «горячий» путь, а не
cold-cache replay.

### 2.4. Метрика только TPS, без латентности

**Проблема.** При сравнении конфигов ВМ две конфигурации могут давать одинаковый средний TPS, но одна с p99 = 50 мс, другая — 2 с. Без распределения латентности это не видно.

**Решение.** В каждом воркере замеряем `time.perf_counter()` вокруг **каждой** транзакции, кладём в список, в конце считаем avg/p50/p95/p99 через `statistics.quantiles(..., n=100)`.

### 2.5. Двойная задержка в `MetricsCollector`

**Проблема.** Внутри `_collect`:
```python
per_cpu = psutil.cpu_percent(interval=1, percpu=True)  # блокируется на 1 сек
...
time.sleep(1)                                          # ещё 1 сек сна
```
Реальный сэмпл-рейт — 0.5 Гц, а не 1 Гц.

**Решение.** Убрать `time.sleep(1)`. `psutil.cpu_percent(interval=1)` уже сам обеспечивает паузу.

### 2.6. Память считалась по всей ВМ

**Проблема.** `psutil.virtual_memory().percent` отвечает на вопрос «сколько RAM занято на ВМ», а не «сколько съел postgres». Если на ВМ работает что-то ещё — метрика бесполезна.

**Решение.** Дополнительно считаем суммарный RSS всех процессов с именем `postgres` через `psutil.process_iter`. В отчёте — обе цифры: системная RAM% и `postgres RSS MB`.

### 2.7. Нет снапшота окружения

**Проблема.** Студент гоняет десяток ВМ-конфигов, копирует stdout в Excel — и потом не помнит, какая версия PG и `shared_buffers` была у конкретного прогона.

**Решение.** В начале каждого прогона собираем `environment`:
- версия PG (`SHOW server_version`),
- ключевые GUC (`shared_buffers`, `effective_cache_size`, `work_mem`, `maintenance_work_mem`, `synchronous_commit`, `wal_compression`, `max_connections`, `data_checksums`),
- `os.cpu_count()`,
- `psutil.virtual_memory().total`,
- результат `uname -r`.

Всё это идёт и в текстовый отчёт, и в JSON.

### 2.8. Отчёт только в stdout

**Решение.** Сохраняем `bench_report_<timestamp>.txt` и `bench_report_<timestamp>.json` в директорию из `BENCH_OUTPUT_DIR` (дефолт — `./reports/`). JSON — машиночитаемый, удобен для агрегации.

### 2.9. Прочее

- `mp.set_start_method('fork', force=True)` оставляем как есть на Linux, но добавляем явный комментарий «на macOS этот код не работает с psycopg2, только Linux».
- `os.cpu_count()` оставляем — в современных гипервизорах он возвращает выделенные vCPU.

## 3. `03_integrity_check.py` — проверка целостности

### 3.1. Счётчики «проверено таблиц/индексов» в финальном отчёте врали

**Проблема.** `report_lines` использовал `len(tables)` / `len(indices)`, а эти переменные после цикла указывают только на **последнюю** обработанную БД. На двух и более базах цифры в отчёте бессмысленны.

**Решение.** Завести счётчики `total_tables_checked`, `total_indices_checked`, `total_indices_skipped` и аккумулировать их по всем БД.

### 3.2. `bt_index_*_check` вызывался на не-btree индексах

**Проблема.** `bt_index_check` и `bt_index_parent_check` работают только с btree. Для GIN/GiST/hash/BRIN/SP-GiST они кидают ошибку, и эта ошибка записывалась как «индекс повреждён» — ложноположительное срабатывание.

**Решение.** В запросе на индексы джойниться к `pg_am` и фильтровать по `am.amname = 'btree'`. Остальные индексы возвращаем отдельным списком «skipped: unsupported access method».

### 3.3. Системная статистика смотрела не туда

**Проблема.** `pg_stat_database.conflicts` и `deadlocks` — это про блокировки и реплику, **не про целостность данных**. Реальный показатель сбоев диска — `pg_stat_database.checksum_failures` (с PG 12+).

**Решение.** Считаем `SUM(checksum_failures)`. Если БД без `--data-checksums` (т.е. `data_checksums = off`) — явно об этом сообщаем в отчёте: «checksums отключены, эта метрика бессмысленна».

### 3.4. f-string с именами объектов

**Проблема.** `cur.execute(f"SELECT verify_heapam('{schema}.{table}');")` формально позволяет SQL-инъекцию, если имя таблицы содержит апостроф. В нашей среде это маловероятно, но это антипаттерн.

**Решение.** `psycopg2.sql` (`SQL`, `Identifier`, `Literal`) для всех динамически подставляемых имён.

### 3.5. Отчёт перезаписывался

**Проблема.** Файл отчёта имел фиксированное имя — каждый запуск затирал предыдущий. Запуск из cron терял историю.

**Решение.** В имя файла подставляется timestamp: `integrity_report_2026-06-03_12-34-56.txt`. Zabbix-JSON остаётся с фиксированным именем (для поллинга), но добавляется второй файл с timestamp — для истории.

### 3.6. `CHECK_HEAP = True` по умолчанию — это часы IO

**Решение.** Дефолт `False`. Включается переменной окружения `CHECK_HEAP=1` или редактированием константы. В README — предупреждение.

### 3.7. Состояние data_checksums

**Решение.** В начале запуска проверяем `SHOW data_checksums`. Если `off` — выводим предупреждение, что отсутствие checksum_failures ничего не значит.

### 3.8. `bt_index_parent_check` берёт ACCESS EXCLUSIVE LOCK на индекс

**Решение.** Если уровень `parent`, в логе явно предупреждаем, что проверка возьмёт эксклюзивный лок на индекс — на проде запускать с осторожностью.

### 3.9. Конфиг — через переменные окружения

**Решение.** Все настройки (`CHECK_HEAP`, `CHECK_INDEX_LEVEL`, `EXCLUDE_DATABASES`, пути отчётов) читаются из окружения с дефолтами в коде.

## 4. `04_corruption_test.py` — новый скрипт

### 4.1. Зачем

`03_integrity_check.py` корректен, но на свежей БД отвечает «всё ок» просто потому, что повреждений нет. Чтобы убедить себя (и студента), что чекер действительно ловит проблемы, нужна управляемая corruption injection.

### 4.2. Как мы ломаем

1. Подключаемся к БД, спрашиваем `pg_relation_filepath('idx_test_data_id')`.
2. Останавливаем postgres (`systemctl stop postgresql`).
3. Копируем relfilenode в `/var/tmp/corruption_backup_<timestamp>/`.
4. Через `dd if=/dev/urandom of=<file> bs=1 count=128 seek=<offset>`
   пишем 128 случайных байт в середину второй страницы (8192 байта = page 0,
   значит seek по 8192 + 128 точно попадёт во вторую страницу).
5. Поднимаем postgres.
6. Запускаем `03_integrity_check.py` — ожидаем ненулевой exit code.
7. Останавливаем postgres, восстанавливаем relfilenode из бэкапа.
8. Поднимаем postgres, запускаем `03_integrity_check.py` — ожидаем `exit 0`.

### 4.3. Защита от самопальной катастрофы

Скрипт ничего не делает, пока в окружении не выставлено `I_UNDERSTAND_THIS_DESTROYS_DATA=yes`. Иначе выходит с инструкцией. Это сознательно длинная переменная, без короткого алиаса.

### 4.4. Что мы НЕ ломаем

- Только относящиеся к `testdb` таблицы/индексы.
- Никогда не трогаем `pg_global`, `pg_default`, `template*`.
- В конце безусловно пробуем восстановить (даже на ошибке) — через try/finally.

### 4.5. Почему именно физическая модификация, а не psql-INSERT с битыми данными

Битый INSERT нельзя получить через SQL — postgres проверяет данные на входе. Реальный corruption — это физическая модификация файла «под» postgres'ом. Поэтому единственный честный способ — менять байты в relfilenode при остановленной БД.

### 4.6. `os.pwrite`, а не `dd` через shell

Первая версия использовала `subprocess.run("dd if=... of={path}", shell=True)` с интерполяцией пути в команду. Это плохо по двум причинам:

1. **Безопасность.** Если в `data_directory` появится пробел/спецсимвол — shell-парсер сломает команду или, хуже, превратит её в инъекцию. Хук security-guidance справедливо выловил это сразу.
2. **Семантика.** `dd` без `conv=notrunc` может усечь файл. Один неверный флаг — и БД не восстановишь.

Заменил на `os.open` + `os.pwrite(fd, payload, offset)`:
- `pwrite` записывает по абсолютному смещению, не двигает file pointer, не растягивает и не усекает файл;
- никакой shell вообще не задействован;
- `os.fsync` гарантирует, что байты улетели на диск до того, как мы запустим postgres обратно.

Все остальные внешние команды (`systemctl`, `pg_isready`, `chown`) тоже переведены на list-форму `subprocess.run([...])` без `shell=True`.
